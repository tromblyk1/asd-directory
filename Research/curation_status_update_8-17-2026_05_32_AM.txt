=== 2. Group on `canonical_city`, never on `city` ===

A canonical_city column plus a BEFORE INSERT OR UPDATE trigger is
live on `resources`, calling public.canonicalize_city(text).

The function uppercases, strips a trailing ", FLORIDA" / ", FL",
returns NULL for anything matching '% COUNTY' and for FLORIDA / FL /
REMOTE / VIRTUAL / ONLINE / STATEWIDE / MULTIPLE FL LOCATIONS /
TAMPA BAY AREA, then applies a 14-branch alias CASE.

286 distinct raw `city` values collapse to 263 canonical values.

Example: ST. PETERSBURG is 36 providers across three spellings
(St. Petersburg 33, Saint Petersburg 2, St Petersburg 1). Group on
raw `city` and it splits into three pages of 33/2/1.

The generator must call canonicalize_city() or replicate its CASE
table.

=== 3. cityCoordinates.json is keyed on the wrong column ===

It must be keyed to canonical_city (263 keys), not city. That is the
actual cause of the missing ST. PETERSBURG entry - not a missing key
so much as the wrong key space. Junk keys (STE102, SR 31) are a
symptom of the same thing.

A corrected file has been produced: 286 keys -> 282, covering all 263
canonical cities. It drops 10 address-fragment keys and 15 alias
spellings that canonicalize_city() already resolves.

CRITICAL - THESE TWO CHANGES SHIP TOGETHER OR NEITHER DOES:
48 keys in the current file are mixed-case (Orlando, Tallahassee,
Lakeland, Hollywood, Pembroke Pines) because the file was originally
built against the raw `city` column, which is title case.
canonical_city is always UPPERCASE. The corrected file is fully
uppercased. Swapping the file without switching the lookup to
canonical_city breaks those 48 cities.

The corrected file is not ready to hand over yet - 21 cities still
carry "_NEEDS_COORDS": true placeholders. Geocoding stalled (see
section 6).

=== 7. DATA QUALITY FINDINGS THAT AFFECT COUNTS ===

DUPLICATE DENSITY IS UNMEASURED. SQL address-matching found 9
duplicate pairs. Independent website verification of just 42 records
found 8 MORE clusters SQL could not see - same physical site stored
with a different address string or a different city label. There is
currently no reliable count of unique providers.

CITY LABELS ARE WRONG AT A MATERIAL RATE. Confirmed cases where
stored city != actual city: id 8573 Miramar->Pembroke Pines,
8582 Palm Springs->West Palm Beach, 8603 Palm Springs->West Palm
Beach, 8557 Holly Hill->Daytona Beach, 8508 Miami->Miami Shores.

Separately, 20 records have a NAME SUFFIX naming a different city
than their address - border clinics marketing under the larger
neighboring city (e.g. "Select Physical Therapy - West Palm Beach" at
a Palm Springs address). Address is treated as truth; the name suffix
is cosmetic but WILL READ AS AN ERROR on generated pages.

GEOCODING IS STALLED. 263 of 3,339 providers had no coordinates
(NOTE: an earlier status doc said 17 - that was wrong, it was a
subset figure). 89 resolved. The remaining ~174 cannot be geocoded -
the Census TIGER index does not carry many Florida vanity street
names (Sunset Dr = SW 72nd St in Miami-Dade), and no alternative
geocoder is reachable from the research environment. These records
keep canonical_city and still appear in city listings; they lose map
pins only.
